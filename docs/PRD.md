# 01 · Kite .NET 支付组件

PRD 1.0 · 2026-10-18 · 卖方接入组件 · 第一批候选  
状态：设计提案，未实现/未付款/未提交。先读[总体接入设计](../总体接入设计.md)与[接口事件约定](../接口与事件约定.md)。

## 1. 用户与真实场景

**用户：**已有 ASP.NET Core API、希望向 Kite Agent 提供收费服务的团队。

**第一次使用：**团队已经提供结构化数据查询。安装 NuGet 包、配置收款方和受保护路由后，让 Passport 客户端完成一次真实购买；上游报错时不结算。

**问题：**业务服务本来可用，但团队需要自行对齐付款协商、网络和资产、代理结果、错误状态与框架中间件顺序。交付物必须是可维护组件，而不止一个能返回 402 的示例。

**Kite 接入价值：**直接实现 Kite x402 卖方接入；独立价值在 C# 类型模型、ASP.NET 管线、契约一致性和诊断。官方主仓只有 TS/Go 模板，不代表社区没有 .NET 包，立项前须检查同类包；成熟同类存在时优先贡献。

## 2. MVP 范围

**P0，首版必须完成：**

- ASP.NET 中间件与独立 NuGet 包，保护 /v1/*，/healthz 免费；只支持一个有界 JSON 代理场景。
- 对接 facilitator 的 supported/verify/settle；网络与资产由受测配置决定，金额全程使用安全十进制及整数 token 单位。
- 保持官方环境变量与主要协议头兼容，代理业务成功后结算；实际不支持的协议版本、流式响应明确拒绝。
- 保存脱敏结算尝试与业务执行结果；重复请求和未知付款状态可核查。

**P1，有真实反馈后再做：**

- 增加路由级价格和项目指标；新增资产或网络必须经过契约测试。
- 补齐第二个真实 .NET 服务案例，依据集成反馈稳定公共 API。

**首版排除：**不写新钱包、签名算法或 facilitator；不承诺流式、多协议或所有网络一开始都支持。

## 3. 完整用户流程

1. 开发者安装包并配置收款地址、上游、价格和网络。
2. CLI 或未付费 HTTP 请求访问付费端点，取得 402 与报价。
3. Passport 用户按真实预检创建并批准会话。
4. 中间件验证付款，再执行业务，检查响应与结果有效性。
5. 结果保存后结算；确认成功才返回完整结果及可见付款凭证。
6. 客户端断开或结算响应丢失时保留未决状态，不盲目新建收费尝试。

## 4. Kite 能力接入

| 官方能力 | 接入方式 | 保存与验证 |
|---|---|---|
| 卖方协议 | 官方 x402 模板约定、facilitator /supported /verify /settle | 协议版本、network、asset、amount、payTo、验证/结算状态 |
| 买方互通 | kpass session execute，参见公共接入设计 | 实际 session、执行结果、付款凭证；不要求卖方保管买方密钥 |
| 服务登记 | service.yaml，source=custom | 清单通过固定 schema；自有 API 作为实际 upstream |

**接入前置：**所有涉及真实付款的路径先完成 G0，固定 network/asset/facilitator/CLI/账户环境；见总体接入设计。真实身份或 Runtime 不可得时明确 blocked，不能用 mock 替代。

**授权边界：**应用与业务权限自己验证；Passport 的 passkey 批准保留给真实用户；本轮 PRD 编制不发起任何授权或支付。协议实例、金额、会话和示例均以现场预检与实际输出为准。

## 5. 接口与数据

**拟提供接口：**拟提供 AddKitePayments(options) 与 UseKitePayments()，名称是本项目设计，不是现有官方 SDK。POST /v1/sample/query 为演示付费路由；GET /healthz 免费。Options 对应 PAY_TO、KITE_NETWORK、UPSTREAM_URL、PRICE_USD 和可选上游鉴权配置。

**核心对象：**RoutePolicy、PriceVersion、PaymentAttempt、BusinessResult、SettlementEvidence。价格版本和请求摘要固定在一次尝试上；日志不保存付款签名原文。

operation_id、付款证据、业务版本及产物按公共事件契约关联。接口/包名属于本项目设计，不代表官方已经发布同名能力。

## 6. 状态与恢复

CHALLENGED → VERIFIED → BUSINESS_SUCCEEDED → SETTLEMENT_PENDING → SETTLED → RETURNED；错误为 VERIFY_REJECTED、BUSINESS_FAILED、PAYMENT_UNKNOWN。后者不等于未付款。

- 上游 4xx/5xx、结果格式无效：不进入结算，返回可区分的业务失败。
- 结算返回超时：把尝试置 PAYMENT_UNKNOWN，依据原始尝试与凭证核查；不换 key 重付。
- 代理不转发内部密钥和逐跳头；限制请求体、方法、目标与超时。客户端取消不当作链上取消。

任何付款未知均不能通过换 key 自动重买；任何产物恢复都需要原权限。测试桩中的假付款不产生真实交付承诺。

## 7. 开发任务拆分

- 01-T01：定义受支持协议与配置、建立官方行为对照表。
- 01-T02：实现请求/响应类型和 facilitator 适配，接入金额处理。
- 01-T03：实现中间件顺序、结果保存和未决状态。
- 01-T04：搭建失败注入契约测试，完成真实互通。
- 01-T05：发布 NuGet、容器示例和清单，找一个外部 .NET 服务集成。

**投入粗估：**4–6 人周。先做 M0 兼容与样本验证，再做独立核心、真实互通及发布；外部批准、环境开通和审核不计入可承诺工期。

## 9. 验收与演示

下面是目标，尚未运行或达成。

- D01：官方模板支持范围内的 402、付费成功及错误语义对照一致。
- D02：错误网络/资产、无效签名、上游失败、结算超时和客户端断连均有断言与证据。
- D03：金额边界与精度无浮点截断，重复业务操作不会因本地重试无条件执行两次。
- D04：NuGet 可安装；独立项目按文档运行。G0 兼容验证通过后完成真实 Passport 调用；未通过就保留阻塞，不声明互通。

**完整演示：**从空 ASP.NET 项目安装包，购买一次查询；再让上游返回 500，展示业务错误与未结算证据。

**试用观察：**外部项目接入步骤、首次互通用时、可重现兼容缺陷及真实使用者反馈。
